## Text Elements
100M new short URLs / month
each stored record ~500 bytes
read:write = 100:1 ^FiMuFCGL

Design URL Shortener
 ^18cbPqUg

Requirements:
1. Functional -> create: long URL -> short code (santization)
    redirect: short code -> long URL ^GNV2S8Uk

read heavy ^ATffIcST

2.Non functional -> we write less than read 
    availability is a must
    low latency on redirect (thats why we cache)
    short codes must be unique ^6XQXVii9

Estimations
    write QPS -> 100M / 2.6M ~ 38/s * 2 ~77/s (peak)
    read QPS -> 100 * 38 ~ 3850/s * 2 ~ 7700/s (peak) 
    storage/year = 100M * 12 = 1.2B / year * 500 bytes  ~ 600 GB/year

for writes -> tiny one db handles the write
for read -> we need cache and read replicas
for storage -> fits 1 DB for years (no sharding needed yet)
 
 ^TWs52Mog

API 
post/ shortner(long_url:str) -> return the short url after santization
get/ redirect(short_code:str) -> redirect the short url with the long one  ^rteAVBZD

Data Model
Columns: 
    long url 
    short code (PK , unique,index)
    created_at

access pattern: we read by short_code
since we look up by the short code so its the index + PK
- read by short code ~100x more than writes -> index short_code + cache it
  ^f3AqtYU2

POST/CREATE ^lTUSvj1V

long_url ^8KJNSAcT

Santization ^2507wrvi

short code (unique) ^kJIw4dsp

Save the long url and 
short code and cache the short code  ^6stZVyLZ

GET/REDIRECT ^pB0Cctbk

We get the short code by lookup in the cache first for fast lookup
if not available in the cache , check db
 ^PsVI2XTS

Redirect using the short code to the long url  ^Rfe9YYBv

Bottleneck
DB reads are the bottleneck , the cache absorbs the most 
+ DB Replicas spread whatever the cache misses

the tradeoff is that replication has replication lag because a replica is slightly left behind the primary, so a just created short link might not be on replica yet 
so we rely on cache for those just created things

what breaks at 10X 
10x read -> cache is a must and may fill quickly so we need more replicas and bigger cache 
10x storage -> eventually a shard will be needed

How will bwe generate the short code so that its unique and at scale without bottleneck:
- Counter + base62  -> global incrementing number encoded to base62 , unique , but the counter is a single point
- Random + check   -> generate random , check db for collision , retry , simple but collisions may happen
- why hash256 is not an option -> too long , we would have to truncate it , truncation brings back the collision so we are just random + check again , hash is deterministic (same url will always make the same code) so it acts a dedup but it will break the real needs 
two users shortening the same url cant get seperate links , no custome coes and the code is predictable
and it also doesnt solve the actual problem we we're solving ^EnLrUe6L
