# MCP Architecture: Design Philosophy & Engineering Principles

Traditional APIs were designed for **predictable, human-designed workflows**

AI systems need:
- **Dynamic resource discovery** (AI doesn’t know what it needs until it needs it)
- **Rich context exchange** (not just data, but metadata, relationships, capabilities)
- **Secure sandboxing** (AI can’t be trusted with direct system access)
- **Bidirectional communication** (AI needs to ask questions, not just consume data)

### Protocol layer 
The protocol layer handles message framing, request/response linking, and high-level communication patterns.

### Transport layer 
The transport layer handles the actual communication between clients and servers. MCP supports multiple transport mechanisms:

1. **Stdio transport**
    
    - Uses standard input/output for communication
    - Ideal for local processes
2. **HTTP with SSE transport**
    
    - Uses Server-Sent Events for server-to-client messages
    - HTTP POST for client-to-server messages

MCP messages
**Request** — one side asks the other to do something and _waits for an answer_.
- `method` is what to run, `params` is the arguments.
- When the model calls your `add-task`, the host sends a Request like `method="tools/call", 
	`params={"name": "add-task", "arguments": {"text": "buy milk"}}`.

**Result** — the successful answer to a Request
It's an open bag of key/values 
Your tool's `return task` becomes the Result that travels back.

**Error** — the answer when the Request failed. 
- `code` is a number (JSON-RPC uses fixed ones, e.g. `-32602` = invalid params, `-32601` = method not found),
- `message` is human-readable, `data` is optional extra detail.
- If your tool raises an exception, the SDK turns it into one of these.

**Notification** — a one-way message that expects _no_ reply. 
- Same shape as a Request (method + params) but nobody answers.
- Example: the server telling the host "my tool list changed" so it refreshes.
- The real difference from a Request isn't the fields, it's that a Request carries an `id` (so the Result/Error can be matched to it) and a Notification has no `id` (nothing to match, nothing comes back).

```python
from typing import Any,Optional
from pydantic import BaseModel

#expects a result or an error
class Request(BaseModel):
	method: str
	params: Optional[dict[str,Any]] = None
	
#Result is a successful response
Result = dict[str,Any]

#error 
class Error(BaseModel):
	code:int
	message:str
	data: Optional[Any] = None
	
#Notification - one way no response
class Notification(BaseModel):
	method:str
	params: Optional[dict[str, Any]] = None
```

## Connection lifecycle 

### 1. Initialization

![[Pasted image 20260910150534.png]]

1. Client sends `initialize` request with protocol version and capabilities
2. Server responds with its protocol version and capabilities
3. Client sends `initialized` notification as acknowledgment
4. Normal message exchange begins

### 2. Message exchange 

After initialization, the following patterns are supported:

- **Request-Response**: Client or server sends requests, the other responds
- **Notifications**: Either party sends one-way messages

### 3. Termination 

Either party can terminate the connection:

- Clean shutdown via `close()`
- Transport disconnection
- Error conditions

## Best practices

### Transport selection 
1. **Local communication**
    
    - Use stdio transport for local processes
    - Efficient for same-machine communication
    - Simple process management
2. **Remote communication**
    
    - Use SSE for scenarios requiring HTTP compatibility
    - Consider security implications including authentication and authorization

### Message handling 

1. **Request processing**
    
    - Validate inputs thoroughly
    - Use type-safe schemas
    - Handle errors gracefully
    - Implement timeouts
2. **Progress reporting**
    
    - Use progress tokens for long operations
    - Report progress incrementally
    - Include total progress when known
3. **Error management**
    
    - Use appropriate error codes
    - Include helpful error messages
    - Clean up resources on errors

## Security considerations 

1. **Transport security**
    
    - Use TLS for remote connections
    - Validate connection origins
    - Implement authentication when needed
2. **Message validation**
    
    - Validate all incoming messages
    - Sanitize inputs
    - Check message size limits
    - Verify JSON-RPC format
3. **Resource protection**
    
    - Implement access controls
    - Validate resource paths
    - Monitor resource usage
    - Rate limit requests
4. **Error handling**
    
    - Don’t leak sensitive information
    - Log security-relevant errors
    - Implement proper cleanup
    - Handle DoS scenarios

## Debugging and monitoring [](https://modelcontextprotocol.info/docs/concepts/architecture/#debugging-and-monitoring)

1. **Logging**
    
    - Log protocol events
    - Track message flow
    - Monitor performance
    - Record errors
2. **Diagnostics**
    
    - Implement health checks
    - Monitor connection state
    - Track resource usage
    - Profile performance
3. **Testing**
    
    - Test different transports
    - Verify error handling
    - Check edge cases
    - Load test servers

Prompts 
Prompts enable servers to define reusable prompt templates and workflows that clients can easily surface to users and LLMs.

- Accept dynamic arguments
- Include context from resources
- Chain multiple interactions
- Guide specific workflows

Structure
```python
{
  name: string;              // Unique identifier for the prompt
  description?: string;      // Human-readable description
  arguments?: [              // Optional list of arguments
    {
      name: string;          // Argument identifier
      description?: string;  // Argument description
      required?: boolean;    // Whether argument is required
    }
  ]
}
```

Discover Prompt
```python
// Request
{
  method: "prompts/list"
}

// Response
{
  prompts: [
    {
      name: "analyze-code",
      description: "Analyze code for potential improvements",
      arguments: [
        {
          name: "language",
          description: "Programming language",
          required: true
        }
      ]
    }
  ]
}
```

Use prompt
```python
// Request
{
  method: "prompts/get",
  params: {
    name: "analyze-code",
    arguments: {
      language: "python"
    }
  }
}

// Response
{
  description: "Analyze Python code for potential improvements",
  messages: [
    {
      role: "user",
      content: {
        type: "text",
        text: "Please analyze the following Python code for potential improvements:\n\n```python\ndef calculate_sum(numbers):\n    total = 0\n    for num in numbers:\n        total = total + num\n    return total\n\nresult = calculate_sum([1, 2, 3, 4, 5])\nprint(result)\n```"
      }
    }
  ]
}
```

## Best practices

When implementing prompts:

1. Use clear, descriptive prompt names
2. Provide detailed descriptions for prompts and arguments
3. Validate all required arguments
4. Handle missing arguments gracefully
5. Consider versioning for prompt templates
6. Cache dynamic content when appropriate
7. Implement error handling
8. Document expected argument formats
9. Consider prompt composability
10. Test prompts with various inputs

### Implementation

A prompt is a decorated function, like a tool. Its parameters become the arguments (no default = required, a default = optional), and returning a string auto-wraps into a user message. The SDK generates `prompts/list` and `prompts/get` for you.

```python
from mcp.server import MCPServer

mcp = MCPServer("example-prompts-server")

@mcp.prompt("git-commit", description="Generate a Git commit message")
def git_commit(changes: str) -> str:
    # `changes` has no default, so it is a REQUIRED argument
    return (
        "Generate a concise but descriptive commit message "
        f"for these changes:\n\n{changes}"
    )

@mcp.prompt("explain-code", description="Explain how code works")
def explain_code(code: str, language: str = "Unknown") -> str:
    # `code` is required; `language` has a default, so it is OPTIONAL
    return f"Explain how this {language} code works:\n\n{code}"
```

Note: returning a plain string gives one user-role text message (the common case). If you need several messages or an assistant role, return a list using v2's `UserMessage` / `AssistantMessage` helpers. Do NOT return raw `PromptMessage` objects here, v2 re-wraps them and you get a garbled nested message.

```python
from mcp.server import MCPServer
from mcp.server.mcpserver import UserMessage, AssistantMessage

mcp = MCPServer("example-prompts-server")

@mcp.prompt("analyze-code", description="Analyze code for improvements")
def analyze_code(code: str):
    return [
        UserMessage(f"Analyze this code:\n\n{code}"),
        AssistantMessage("Sure, here is the analysis:"),
    ]
```

Note: prompts are the same pattern as tools and resources in v2. Tool = the model *does* something (`@mcp.tool`). Resource = the model *reads* data (`@mcp.resource`). Prompt = a reusable template the user/model can pick (`@mcp.prompt`). All three are just decorated functions on the same `mcp` object.

# Best practices

Learned from reading `approve_draft.ts` in the real Shutterabia MCP server, ported to Python v2. All code below is checked against the installed `mcp` 2.x.

## 1. Thin handler, real work in a pure function

The tool only validates, calls an internal function, formats, and catches. The logic lives in a plain function you can test without a server and reuse from a second entry point.

```python
# pure logic — no MCP, easy to test
def approve_draft_internal(ctx, draft):
    ctx.db.update_draft_status(draft.id, "approved")
    return ctx.db.get_draft(draft.id) or draft

@mcp.tool("approve-draft", description="Approve a staged draft.")
def approve_draft(draft_id: str) -> str:
    draft = ctx.db.get_draft(draft_id)
    approve_draft_internal(ctx, draft)     # <- handler stays thin
    return f"Draft {draft_id} approved."
```

## 2. Inject a `ctx`, never module globals

Bundle dependencies into one object and pass it into a `register_x(mcp, ctx)` function. No `global`, no import-order traps (this is what caused my `UnboundLocalError` and off-by-one in the task server).

```python
from dataclasses import dataclass

@dataclass
class ToolContext:
    db: "AppDatabase"
    # brands, media paths, etc.

def register_approve_draft(mcp, ctx: ToolContext) -> None:
    @mcp.tool("approve-draft", description="Approve a staged draft.")
    def approve_draft(draft_id: str) -> str:
        draft = ctx.db.get_draft(draft_id)   # ctx closed over, no globals
        ...
```

## 3. Validate inputs with real constraints

A bare `str` accepts an empty string. Use `Annotated[..., Field(...)]` so bad input is rejected before your code runs.

```python
from typing import Annotated
from pydantic import Field

@mcp.tool("approve-draft", description="Approve a staged draft.")
def approve_draft(draft_id: Annotated[str, Field(min_length=1)]) -> str:
    ...
```

## 4. Write the description for the model

The description and the argument names are the model's only guidance. Put the behavior rules there.

```python
@mcp.tool(
    "approve-draft",
    title="Approve a draft",
    description=(
        "Mark a staged draft as approved. Call this only AFTER the human has "
        "explicitly approved the content in chat. Approval is required before "
        "create-post or schedule-post will act."
    ),
)
def approve_draft(draft_id: str) -> str:
    ...
```

## 5. Log to stderr, return for the model

`print` corrupts stdio. `logger` goes to stderr (for you). The `return` is the only thing the model sees.

```python
import logging
logger = logging.getLogger(__name__)

@mcp.tool("approve-draft", description="Approve a staged draft.")
def approve_draft(draft_id: str) -> str:
    logger.info("approving %s", draft_id)   # for me, in the terminal
    return f"Draft {draft_id} approved."    # for the model
```

## 6. Enforce the rule in code, not the prompt (the gate)

The biggest one. A publish tool refuses unless the draft is approved. A confused model gets an error, not a bad action. Guidance is a hint, the code is the wall.

```python
@mcp.tool("create-post", description="Publish an approved draft now.")
def create_post(draft_id: str) -> str:
    draft = ctx.db.get_draft(draft_id)
    if draft.status != "approved":
        raise ToolError("Refusing to publish: draft is not approved yet.")
    ...  # only reached when the gate passes
```

## 7. Guard clauses first, fail fast

Check "not found", "wrong state", "already done" at the top and return/raise early. The happy path comes last.

```python
@mcp.tool("approve-draft", description="Approve a staged draft.")
def approve_draft(draft_id: str) -> str:
    draft = ctx.db.get_draft(draft_id)
    if draft is None:
        raise ToolError(f'No draft found with id "{draft_id}".')
    if draft.status == "rejected":
        raise ToolError(f'Draft "{draft_id}" was rejected and cannot be approved.')
    approve_draft_internal(ctx, draft)       # happy path last
    return f"Draft {draft_id} approved."
```

## 8. Two error kinds, handled differently

Expected refusal → `raise ToolError("clear message")` (the SDK reports it cleanly to the model). Unexpected crash → log the technical detail to stderr, return/raise a generic message. Never leak internals. (A plain `raise ValueError` becomes an `UnexpectedToolError` — use `ToolError` for expected refusals.)

```python
from mcp.server.mcpserver.exceptions import ToolError

@mcp.tool("approve-draft", description="Approve a staged draft.")
def approve_draft(draft_id: str) -> str:
    try:
        draft = ctx.db.get_draft(draft_id)
        if draft is None:
            raise ToolError(f'No draft found with id "{draft_id}".')  # expected
        return f"Draft {draft_id} approved."
    except ToolError:
        raise                                    # expected refusal, pass through
    except Exception as e:
        logger.exception("approve_draft failed")  # unexpected, detail to stderr
        raise ToolError("Could not approve the draft.")  # generic to the model
```

## 9. One tool per file + a register barrel

Overkill at 3 tools, essential at 20. Each tool is its own file with a `register_x`; one barrel wires them all.

```python
# tools/__init__.py
def create_tools(mcp, ctx) -> None:
    register_approve_draft(mcp, ctx)
    register_stage_draft(mcp, ctx)
    register_create_post(mcp, ctx)
    # ...one line per tool
```

## 10. Audit every state change, and guard irreversible actions

Log each change, and block a duplicate before anything that publishes.

```python
def approve_draft_internal(ctx, draft):
    ctx.db.update_draft_status(draft.id, "approved")
    ctx.db.append_log(event="draft_approved", detail={"draft_id": draft.id})  # audit

@mcp.tool("create-post", description="Publish an approved draft now.")
def create_post(draft_id: str, allow_duplicate: bool = False) -> str:
    if not allow_duplicate and ctx.db.find_blocking_post(draft_id):
        raise ToolError("This draft was already published. Pass allow_duplicate=True to repeat.")
    ...
```
