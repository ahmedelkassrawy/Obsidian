# Durable Ingestion in raaaaag (M5 W2)

> Prerequisite: [[1. Temporal Core Concepts]] (server / client / task-queue / worker / workflow / activity / retry / timeouts / sandbox / determinism). This note is the **applied layer** — the decisions, not the mechanics.

## The problem
raaaaag's ingestion is: **read a doc → chunk → embed via Cohere (paid API) → write to pgvector.** For 751 chunks that's long and the embed calls cost money and time. A plain script that crashes at chunk 400 loses all progress — re-run = re-embed 1–400 (wasted $ + time) or worse, double-insert. That's the textbook Temporal case: **long, multi-step, stateful, expensive-to-repeat.**

## Decision 1 — what to make durable (the senior call)
The system has two long paths. Only one needs Temporal:

| Path | Durable via | Why |
|---|---|---|
| **Ingestion** (chunk→embed→store) | **Temporal** ← W2 | long, expensive external calls, must resume mid-flow |
| **The answer loop** (retrieve→rerank→generate) | **LangGraph checkpointer** (W1) | already durable — `MemorySaver`/`thread_id` saves state each step and resumes |

**Do not wrap the agent loop in Temporal** — it's already durable from Week 1. Knowing *not* to double up is the point. Temporal goes around ingestion; the checkpointer already covers the loop.

## Decision 2 — activity granularity (the "middle ground")
One activity per *what*? Options:
- **per chunk** → resume at the exact chunk, but 751 activities = huge history/overhead.
- **per document** → tiny history, but a crash re-does the whole current doc.
- **per BATCH of ~50 chunks (chosen)** → resume loses ≤50 chunks, ~15 activities for 751, AND Cohere's embed API takes a *list* so batching is free speed. Wins on resume granularity **and** efficiency — not a compromise, the right design for two independent reasons.

```python
BATCH_SIZE = 50
for start in range(0, len(chunks), BATCH_SIZE):
    batch = chunks[start:start + BATCH_SIZE]
    await workflow.execute_activity(embed_and_store, args=[batch, source], ...)
```
Each batch is its own activity → its result is persisted → a crash resumes at the first **unfinished** batch; completed batches are skipped by history replay.

## Decision 3 — idempotency (why durable ≠ safe on its own)
The trap: an activity **writes 50 rows, succeeds, but the ack is lost** → Temporal thinks it failed → retries → **double-insert**. Durability alone doesn't stop this; the *write* must be idempotent.

Fix = a **stable, deterministic key per chunk** + an upsert that no-ops on conflict:
```python
def _chunk_uid(source, page, chunk_index):
    return hashlib.sha256(f"{source}|{page}|{chunk_index}".encode()).hexdigest()

# in embed_and_store:
stmt = pg_insert(Document).values(rows).on_conflict_do_nothing(index_elements=["chunk_uid"])
```
**Two safety layers together:**
1. **Temporal** skips activities that already *completed* (history replay) — the coarse layer.
2. **The upsert** catches a retry of an activity that *wrote but never acked* — the fine layer.

This is the M4 idempotency lesson made load-bearing: same request → same key → repeat is a no-op. (Content/position hash also dedupes a genuinely-repeated intent; a production system would use a client-supplied idempotency key instead.)

## The Celery vs Temporal vs neither rule (memorize)
- **Celery** = fire-and-forget background jobs + simple retries. Worker dies mid-job → progress lost, whole task re-runs (or you rebuild state yourself).
- **Temporal** = long, multi-step, *stateful* workflows that must survive a crash and **resume mid-flow**; persists each step's result so completed steps don't re-run.
- **Neither** = short/single-step work — a plain DB row + your own loop is enough. Don't bolt a workflow engine onto a 2-step job.

## Proven vs design-guaranteed (honest)
- **Proven live:** pipeline runs end-to-end (239 chunks: ch3=84, ch4=65, ch5=90), every row carries a `chunk_uid`.
- **Design-guaranteed, not filmed:** crash-mid-run-and-resume. It's not hand-wavy — the code follows Temporal's contract (workflow deterministic, all I/O in activities, per-batch activities, idempotent writes), so replay skips completed work automatically. The live Ctrl-C would only *show* a guarantee the structure already gives.

## Gotchas from this build
- **Legacy rows:** `chunk_uid` added as `nullable=True` so the 751 existing M1 rows stay valid (Postgres allows many NULLs under a unique index); only durable-pipeline rows get a uid.
- **`create_all` won't add a column** to an existing table — needed an explicit `ALTER TABLE documents ADD COLUMN chunk_uid`.
- **Dev server, not the full stack:** `temporal server start-dev` (in-memory, UI on :8233) is enough to learn durability; the `temporalio/auto-setup` compose (its own DB) is for persistence across a *server* restart.
- **Sandbox imports:** activities imported in the workflow file go through `with workflow.unsafe.imports_passed_through():`.
- **PPTX support:** `chunk_document` dispatches by extension (PyPDFLoader for .pdf, python-pptx per-slide for .pptx) since the OS corpus is PPTX.
