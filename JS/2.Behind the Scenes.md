## What JavaScript is under the hood

This section walks through the properties that describe JavaScript as a language and what each one gives you.

### High level

Every program needs computer resources like memory and CPU. In JavaScript you don't manage any of them yourself; the language does it for you. The cost is that the result isn't as fast or as optimized as code in a low-level language.

### Garbage collected

JavaScript cleans up memory for you, so you never have to free it by hand.

> [!definition] Garbage collection
> An automatic process that removes values from memory once the program no longer uses them.

### Interpreted or just-in-time compiled

Your code is converted to machine code inside the JavaScript engine. How that happens is covered in [[#How the engine turns code into machine code]].

### Multi-paradigm

> [!definition] Paradigm
> An approach to structuring code. It shapes your coding style and technique.

The most popular paradigms are:

- **Procedural programming:** what we've been doing so far
- **Object-oriented programming (OOP)**
- **Functional programming**

JavaScript supports all three.

### Prototype-based object oriented

Almost everything in JavaScript is an object. The exceptions are primitive values like numbers and strings.

Arrays are objects too, which explains why you can call methods like `push` and `pop` on them. Every array is created from an array blueprint called a **prototype**. That prototype holds all the array methods, and each array inherits them from it.

> [!definition] Prototypal inheritance
> Objects get their methods by inheriting them from a prototype object. That's how every array gets `push`, `pop`, and the rest.

### First-class functions

In a language with first-class functions, functions are treated as ordinary values, just like variables. You can pass them into other functions and return them from functions.

### Dynamically typed

You don't declare data types. A variable's type becomes known only at runtime.

### Single-threaded with a non-blocking event loop

> [!definition] Concurrency model
> How the JavaScript engine handles multiple tasks that happen at the same time.

JavaScript needs a concurrency model because it runs on a single thread, so it can only do one thing at a time. A long-running task would seem to block that thread, yet we want non-blocking behavior.

The answer is the **event loop**. It takes long-running tasks, runs them in the background, and puts them back on the main thread once they finish.

## The JavaScript engine and runtime

> [!definition] JavaScript engine
> The program that executes JavaScript code.

Every JavaScript engine contains two parts:

| Part | What it does |
| --- | --- |
| **Call stack** | Where your code is executed, using something called an execution context |
| **Heap** | An unstructured memory pool that stores all the objects your application needs |

### Compilation vs interpretation

A processor only understands zeros and ones, which is machine code. So every program has to be converted to machine code before it runs. There are two classic ways to do that.

> [!definition] Compilation
> The entire source code is converted into machine code at once and written to a binary file the computer can execute.

```text
Source code → compilation → machine code → execution → program running
```

> [!definition] Interpretation
> An interpreter goes through the source code and executes it line by line.

```text
Source code → executed line by line → program running
```

Interpreted languages are much slower than compiled ones.

### Just-in-time compilation

Modern JavaScript uses a hybrid of both approaches.

> [!definition] Just-in-time (JIT) compilation
> The entire code is converted into machine code at once and then executed immediately.

The difference from regular compilation is timing:

- **Compilation:** execution can happen any time after the code is compiled.
- **JIT:** execution happens immediately after compilation.

### How the engine turns code into machine code

1. **Parsing.** The engine reads the code and parses it into a data structure called an **abstract syntax tree (AST)**. It splits each line into pieces that mean something to the language, like the `const` or `function` keywords, and stores them in the tree in a structured way. This step also checks for syntax errors.
2. **Compilation.** The engine takes the AST and compiles it into machine code.
3. **Execution.** The machine code runs right away, in the call stack.

> [!definition] Abstract syntax tree (AST)
> A tree-shaped representation of your code, broken into meaningful pieces. The engine later uses it to generate machine code.

Modern engines also have a clever optimization strategy. They first produce a very unoptimized version of the machine code, just to get the program running quickly. Then, while the program is already running, they optimize and recompile the code in the background, sometimes several times. Each time, the optimized version replaces the unoptimized one.

> [!note]
> All of this happens in special threads that you can't access from your code.

### The JavaScript runtime in the browser

> [!definition] JavaScript runtime
> A container with everything you need to use JavaScript. In the browser, the runtime is the browser itself.

The engine alone isn't enough. It also needs access to the **Web APIs**, which are features the browser provides to the engine. You reach them through the `window` object.

Web APIs are part of the runtime because the runtime is the box that holds all the JavaScript-related pieces you need.

A typical runtime also includes a **callback queue**. This is a data structure holding callback functions that are ready to be executed.

For example, when you attach an event handler function to a DOM element like a button, that handler is a callback function. When the event happens (a click, say), the callback gets called. Behind the scenes:

1. After the event fires, the callback function is put into the callback queue.
2. When the call stack is empty, the callback is passed to the call stack.
3. The callback executes there.

> [!definition] Event loop
> The mechanism that takes callback functions from the callback queue and puts them on the call stack so they can run. This is how JavaScript's non-blocking concurrency model is implemented.

> [!note]
> *Why* this makes JavaScript non-blocking gets its own lecture on the event loop later in the course. Every developer needs to understand it deeply.

### Other runtimes: Node.js

The course focuses on JavaScript in the browser, but JavaScript also runs outside browsers, for example in Node.js.

The Node.js runtime looks similar. It has no browser, so it can't have the Web APIs, since the browser is what provides them. Instead it has multiple **C++ bindings** and a **thread pool**. The details don't matter here. The point is that different JavaScript runtimes exist.

> [!tip] Engine vs runtime
> - **Engine:** call stack + heap. It executes the code. Google's **V8** powers both Chrome and Node.js.
> - **Runtime:** the engine plus everything around it. In the browser that's the Web APIs and callback queue; in Node.js it's C++ bindings and a thread pool.

## Execution contexts and the call stack

This section answers how JavaScript code is actually executed. We know it happens in the call stack inside the engine. Here's the detail, starting right after the code has finished compiling.

### The global execution context

Once the code is ready, the engine creates a **global execution context** for the top-level code.

> [!definition] Top-level code
> Code that isn't inside any function. Only this code runs at first; the code inside a function runs only when that function is called.

The course's Pig Game project shows this. It had an `init` function that set up the game, but to set it up on the first page load, `init()` had to be called right away in the top-level code.

When the engine meets a function declaration or function expression in top-level code, it declares the function so it can be called later. The function's body doesn't run yet.

### What an execution context is

> [!definition] Execution context
> An abstract concept: the environment where a piece of JavaScript is executed. Think of it as a box that stores everything a piece of code needs to run, such as local variables or the arguments passed into a function. JavaScript code always runs inside an execution context.

> [!example] The pizza analogy
> You order a pizza at a takeaway. It comes in a box, along with cutlery and a receipt.
> - The pizza is the code to execute.
> - The box is the execution context, the environment where the eating happens.
> - The cutlery and receipt are what you need to eat the pizza, i.e. what the code needs to run.

Key facts:

- There's only ever **one global execution context** per project, no matter how large the project is. It's the default context, and top-level code runs there.
- Once the context exists, the top-level code executes. Execution itself is simply the CPU processing the machine code it received.
- After the top-level code finishes, functions start running. **Every function call creates a new execution context** holding what that call needs. Methods work the same way, since they're just functions attached to objects.
- All these execution contexts together make up the **call stack**.
- When all functions are done, the engine waits for callback functions to arrive (for example, one tied to a click event) and runs them. The event loop is what delivers them.

### What's inside an execution context

1. **Variable environment**
   - All variable and function declarations.
   - A special `arguments` object with every argument passed into the function the context belongs to.
2. **Scope chain**
   - References to variables that live *outside* the current function. This is how a function can use variables declared outside it. Scoping gets its own lecture later in the section.
3. **The `this` keyword**
   - A special variable every context gets. It also gets its own lecture later.

> [!definition] Creation phase
> The step right before execution where the engine builds the context's contents: variable environment, scope chain, and `this`.

> [!warning] Arrow functions are different
> Execution contexts for arrow functions don't get their own `arguments` object or their own `this`. An arrow function uses the `arguments` and `this` of its closest regular (non-arrow) parent function. The course stresses this as an important detail to remember.

The real internals are even more complex, but this model is enough for now.

### Simulating the creation phase

The lecture walks through a small program with one top-level variable (`name`), two functions (`first` and `second`), and a top-level `x` set to the result of calling `first()`. Something like this:

```javascript
const name = 'Jonas';

const first = () => {
  let a = 1;
  const b = second(7, 9);
  a = a + b;
  return a;
};

function second(x, y) {
  var c = 2;
  return c;
}

const x = first();
```

> [!note]
> The transcript describes this code but doesn't show it. The block above is rebuilt from that description, so the exact names and values may differ from the course slide.

This program gets three execution contexts: one global, plus one for each function.

| Context | Variable environment |
| --- | --- |
| Global | `name`, the `first` and `second` declarations, `x` (unknown until `first()` runs) |
| `first()` | `a = 1`, `b` (unknown until `second()` runs) |
| `second()` | `c = 2`, plus `arguments` holding `[7, 9]` because it's a regular function |

For the functions, the variable environment effectively holds all of that function's code.

> [!warning] A simplification
> Technically none of these values are known during the creation phase. They only become known in the execution phase. The table shows them early just to illustrate what each context holds.

### The call stack

With hundreds of execution contexts for hundreds of functions, the engine needs to know the order functions were called in and where it currently is. That's the call stack's job. Together with the memory heap, it makes up the JavaScript engine.

> [!definition] Call stack
> The place where execution contexts are stacked on top of each other to track where we are in the program. The context on top is the one currently running. When it finishes, it's removed, and execution goes back to the context below.

To extend the pizza analogy: you and some friends each buy a pizza and stack the boxes on top of each other, so you can keep track of whose pizza is whose.

### Walking through the call stack

Using the example above:

1. **Top-level code starts.** The global execution context is created and pushed onto the call stack. It's on top, so it's the one executing.
2. **Simple declarations run.** `name` is declared, then `first` and `second`. Nothing unusual.
3. **`const x = first();`** calls `first`. A new execution context is created for it and pushed on top. It becomes the current context.
4. **Inside `first`**, `a` is declared in *`first`'s* variable environment, not the global one.
5. **`second(7, 9)` is called.** A new context is created, pushed on top, and becomes active.
   - `first` is now **paused** at the point where it called `second`. It only continues once `second` returns. JavaScript has a single thread of execution, so it can do only one thing at a time.
6. **`second` returns.** Its context is popped off the stack and disappears from memory, at least for now (a popped context can actually stay in memory, which comes up later in the course). `first`'s context becomes active again, and execution resumes where it left off.
7. **`first` finishes its calculation and returns.** Its context is popped, and the global context is current again. The returned value is assigned to `x`.
8. **The program stays in this state** until it's really finished, i.e. when you close the browser tab or window. Only then is the global context popped too.

> [!tip] The call stack as a map
> Without the call stack, the engine wouldn't know which function was running before, or where to go back to. It works like a map for the engine, making sure the order of execution never gets lost.

To be precise, code runs inside the execution contexts that sit on the call stack. Saying "JavaScript code runs in the call stack" is still correct in general.
