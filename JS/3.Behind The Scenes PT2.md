Another pitfall for the `this` keyword is when having a function inside of a method
```javascript
const jonas = {
	firstName: "Jonas",
	year:1991,
	calcAge: function() {
		console.log(this);
		console.log(2037 - this.year);
		
		const isMillenial = function() {
			console.log(this.year >= 1981 && this.year <= 1996);
		};
		isMillenial();
	},
	greet: () => {
		console.log(this);
		console.log(`Hey ${this.firstName}`);
	},
};

jonas.greet();
jonas.calcAhe();
```

**Problem 1: `greet` is an arrow function, so it doesn't get its own `this`**

```
jonas.greet(); // logs window, then "Hey undefined"
```

A regular method gets `this` from whatever is left of the dot when you call it, so `jonas.greet()` would make `this` equal `jonas`. Arrow functions skip that rule. They use the `this` from the code around them, and here that's the top level of the file, not the object. The `{ }` of an object literal isn't a scope, so it doesn't count.

In a browser script, top-level `this` is `window`. `window.firstName` doesn't exist, so you get `"Hey undefined"`. That's a quiet bug, not a crash.

**Problem 2: `isMillenial` is a plain function call, so `this` is lost**

Once you fix the typo to `jonas.calcAge()`:

```
calcAge: function () {
  console.log(this);              // jonas ✅ (called as jonas.calcAge())
  console.log(2037 - this.year);  // 46 ✅

  const isMillenial = function () {
    console.log(this.year >= 1981 && this.year <= 1996);
  };
  isMillenial(); // nothing to the left of the dot!
}
```

`isMillenial()` is called on its own, with no object in front of it. A regular function called like that gets `this = undefined` in strict mode, which is the default in modules and classes. So `this.year` throws `TypeError: Cannot read properties of undefined (reading 'year')`. Outside strict mode, `this` falls back to `window` and you quietly get `false`.

**The fix is the opposite tool for each case**

```
const jonas = {
  firstName: "Jonas",
  year: 1991,
  calcAge: function () {
    console.log(2037 - this.year);

    // Arrow function: borrows calcAge's `this`, which is jonas
    const isMillenial = () => {
      console.log(this.year >= 1981 && this.year <= 1996);
    };
    isMillenial(); // true
  },
  // Regular function: gets `this` from the call, jonas.greet()
  greet: function () {
    console.log(`Hey ${this.firstName}`);
  },
};

jonas.greet();   // "Hey Jonas"
jonas.calcAge(); // 46, true
```

So the rule is: **don't use an arrow function as a method, but do use one for a helper function inside a method.** Inside the method, the arrow function borrows the method's `this`, and that's exactly what you want there.

or the second solution is using self.
Use **`const self = this` inside `calcAge`**, then use `self` inside the inner function:
```javascript
const jonas = {
  firstName: "Jonas",
  year: 1991,

  calcAge: function () {
    console.log(2037 - this.year); // 46

    const self = this; // self refers to jonas

    const isMillenial = function () {
      console.log(self.year >= 1981 && self.year <= 1996);
    };

    isMillenial(); // true
  },

  greet: function () {
    console.log(`Hey ${this.firstName}`);
  },
};

jonas.greet();   // Hey Jonas
jonas.calcAge(); // 46, true — fixed calcAhe typo

```

Here’s why it works:

1. Calling `jonas.calcAge()` makes `this` inside `calcAge` refer to `jonas`.
2. `const self = this` stores that same object reference in `self`.
3. The inner function can access variables from its surrounding function, so it can access `self`.

**We haven’t changed the inner function’s `this`. We use `self` to reach `jonas` instead.** Also, `self` isn’t a keyword—you could name it `that` or `jonasReference`.

### Primitive and Reference Types

The big difference is what gets copied when we assign one variable to another:
- With a **primitive**, we copy the primitive value.
- With an **object**, we copy a reference to the same object. We do not create a new object.

![[Pasted image 20261010192311.png]]

#### 1. Primitive values: changing one variable does not change the other

Primitive types are:
- `number`
- `string`
- `boolean`
- `undefined`
- `null`
- `symbol`
- `bigint`

```javascript
let age = 30;
const oldAge = age;

age = 31;

console.log(age);    // 31
console.log(oldAge); // 30
```

At `const oldAge = age`, the value of `age` is still `30`, so `oldAge` gets `30`.
When we later assign `31` to `age`, only `age` changes. `oldAge` keeps its previous value.

The same thing happens with strings:

```javascript
let lastName = 'Williams';
const oldLastName = lastName;

lastName = 'Davis';

console.log(lastName);    // Davis
console.log(oldLastName); // Williams
```

> [!important] Reassignment is different from mutation
> Primitive values are immutable: we cannot change the value itself. `lastName = 'Davis'` reassigns the variable to a different string; it does not mutate the string `'Williams'`.

#### 2. Objects: two variables can refer to the same object

Objects are often called **reference types** in this lesson. These include object literals, arrays, and functions.

```javascript
const me = {
  name: 'Jonas',
  age: 30,
};

const friend = me;
friend.age = 27;

console.log(friend.age); // 27
console.log(me.age);     // 27
console.log(friend === me); // true
```

Why did `me.age` change even though we only wrote `friend.age = 27`?

1. `{ name: 'Jonas', age: 30 }` creates one object.
2. `me` refers to that object.
3. `const friend = me` copies the reference, so `friend` refers to the **same object**.
4. `friend.age = 27` changes that shared object's property.
5. Reading `me.age` or `friend.age` reaches the same property, so both give `27`.

==There are two variable names, but only one object.==

#### 3. Behind the scenes: the lecture's stack and heap model

Recall the JavaScript engine model:
- **Call stack:** tracks function calls and their execution contexts.
- **Heap:** memory used for objects.

The lecture represents primitive values and object references in the stack, with the objects themselves in the heap.

For the primitive example, imagine `age` initially points to a slot containing `30`. `oldAge` also gets the value `30`. After `age = 31`, the diagram gives `age` a different slot containing `31`, while `oldAge` still has `30`.

For the object example, the variable holds a reference that lets JavaScript find the object in the heap. Copying that reference gives another variable access to the same object. Changing a property changes the object, rather than replacing either variable's reference.

> [!note] Treat memory addresses as a teaching model
> The lecture's addresses such as `0001` and `D305` help explain the behavior. JavaScript does not guarantee that all primitives live on the stack or that every reassignment allocates a new memory slot. Actual storage depends on the engine. The reliable rule is: **assignment copies a value; for an object, that value is a reference to the object.**

#### 4. Why can we change an object declared with `const`?

`const` prevents **reassigning the variable**. It does not freeze the object that the variable refers to.

```javascript
const jessica = {
  firstName: 'Jessica',
  lastName: 'Williams',
  age: 27,
};

const marriedJessica = jessica;
marriedJessica.lastName = 'Davis'; // Allowed: mutate the object

console.log(jessica.lastName);        // Davis
console.log(marriedJessica.lastName); // Davis

// marriedJessica = {}; // TypeError: Assignment to constant variable
```

Changing `marriedJessica.lastName` keeps the same reference and modifies a property on the object.
Assigning `marriedJessica = {}` would replace the reference with one pointing to a new object, which `const` forbids.

With `let`, reassignment would be allowed. It would make that variable refer to the new object; it would not replace the original object for other variables.

#### 5. Copying an object with `Object.assign`

To change one object without changing the other's top-level properties, we need a separate object:

```javascript
const jessica2 = {
  firstName: 'Jessica',
  lastName: 'Williams',
  age: 27,
  family: ['Alice', 'Bob'],
};

const jessicaCopy = Object.assign({}, jessica2);
jessicaCopy.lastName = 'Davis';

console.log(jessica2.lastName);    // Williams
console.log(jessicaCopy.lastName); // Davis
console.log(jessica2 === jessicaCopy); // false
```

`Object.assign(target, source)` copies the source's own enumerable properties into the target and returns the target.
Here, `{}` creates a new target object, so `jessicaCopy` and `jessica2` are separate objects.

Their `lastName` properties contain primitive strings. Replacing `jessicaCopy.lastName` does not change `jessica2.lastName`.

> [!warning] `Object.assign` creates a shallow copy
> It copies property values at the first level. If a property contains an object or array, it copies that reference, rather than creating another nested object or array.

#### 6. The shallow-copy problem: nested arrays are still shared

Continue with the same objects:

```javascript
console.log(jessica2.family === jessicaCopy.family); // true

jessicaCopy.family.push('Mary');
jessicaCopy.family.push('John');

console.log(jessica2.family);    // ['Alice', 'Bob', 'Mary', 'John']
console.log(jessicaCopy.family); // ['Alice', 'Bob', 'Mary', 'John']
```

The outer objects are separate, but both `family` properties refer to the same array.
`push()` mutates that array, so both objects show the new members.

- `jessica2 !== jessicaCopy`: separate outer objects.
- `jessica2.family === jessicaCopy.family`: one shared nested array.

A **deep clone** would also copy nested objects and arrays, so changes inside the copy would not affect the original. The lecture postpones this topic and mentions Lodash as a library with a deep-cloning tool.

> [!summary] Remember these differences
> - Copying a primitive gives another variable that primitive value.
> - `const friend = me` copies a reference, so both variables share one object.
> - `const` blocks reassignment, but allows object mutation.
> - `Object.assign({}, object)` makes a new outer object, while nested objects and arrays remain shared.
