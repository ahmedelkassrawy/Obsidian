How the content pipeline works, station by station

One week of X posts for a smart contract audit firm: 3 technical threads and 3 marketing posts, researched, written, checked, reviewed, illustrated and exported to posts.csv. This guide follows one run from the command line to the summary, names the file behind every step, and ends with interview answers.

The design rules behind every choice

Rules in code, judgment in the model

Anything code can check exactly (banned words, length, citation ids, routing, budget) is code. Models only do what needs judgment: research decisions, writing, scoring, choosing image text.

Instructions are files

Prompts, rubrics, brand rules and post types live in .md and .yaml files. A new post type is a new folder, with no orchestrator change.

Nothing unsupported ships

Every claim cites a source id; code checks the id exists; the reviewer checks the text is supported; a broken review fails closed.

One failure never stops the run

Each post ends in exactly one state: shipped, dropped_quality, failed_research, failed_api, failed_budget or failed_output. The other lanes keep going.

Plan

02

Research

MIXED Two graph nodes. The only place the model picks its own next step.

Node 1 · focused_research

Slots with a topic (thread_1 "reentrancy", thread_2 "oracle manipulation") run in parallel.

  1. CODE BM25 search of the knowledge base, top 5
  2. LLM up to 5 turns: finish, search_kb or web_search
  3. CODE runs each search, max 4
  4. CODE checks every cited source was found with status ok

Node 2 · topic_selection

Empty slots get topics.

  1. LLM one batch call proposes a topic per slot, excluding taken topics and the last 4 runs
  2. CODE assign_topics validates and fills any gap itself
  3. CODE shortcut: picked from the list, so the evidence card is ready. No search, no LLM
flowchart LR
  F["focus text from a human"] --> K["code: BM25 top 5"]
  K --> L{"LLM: covered?"}
  L -->|"yes"| P["pack: KB card"]
  L -->|"no"| WS["code: Tavily, else ddgs + page fetch"]
  WS --> L
  E["empty slot"] --> T["LLM batch pick + code check"]
  T --> S["shortcut pack, no search"]
Why focused slots search but empty slots don't: an empty slot's topic was picked from the knowledge base's own list, so its card exists. A focused slot is free text, and nobody knows yet whether the knowledge base covers it.
Why aliases matter: BM25 matches words, not meaning. "rigging the exchange rate" shares no words with KB-18 "Price oracle manipulation", so without aliases KB-18 never reaches the top 5 and the model goes to the web.

Evidence card (SourceRecord): source_id (KB-18, STAT-01, WEB-3f9a…), kind, title, url, evidence_text (max 12,000 chars), status ok or fetch_failed. Web URLs are checked to be public addresses only (SSRF protection), and pages are cleaned with trafilatura.

04

Validator

CODE Free, instant, same answer every time. Fix, then number, then check.

1 · Safe fixes (logged, original kept)

  • banned_characters: em dash → ", " or a space; URLs untouched
  • whitespace: collapse spaces
  • curly_quotes: curly → straight
  • trailing_hashtags: only a block at the very end

3 · Checks (any one rejects)

  • Cited ids exist in this pack with status ok
  • Tweet count within units
  • No source id leaked into the text
  • Banned phrases (whole words, any case), banned characters, hashtags, link domain allow-list
  • X weighted length ≤ limit (links count 23)

2 · Numbering is added before the checks, so the 280 limit includes "3/7 " and the approved text is exactly the exported text.

"5/7 This fix is guaranteed. Details at KB-18 https://evil.io/oracle"
  → tweet_5:leaked_source_id:KB-18
  → tweet_5:banned_phrase:guaranteed
  → tweet_5:link_domain:evil.io
  accepted: false → reviewer skipped → back to the writer

On a length failure the writer also gets measurements: weighted_length:312/280:shorten_by_at_least:32. The reviewer can only read the draft through audit.approved(), which raises if it wasn't accepted.

Doc drift: DESIGN.md §6.11 says replacing an em dash isn't safe. The code later made it a context-aware safe fix (plan step S9).

05

Reviewer

LLM The model judges; code decides. It never says "approved".

Rubric (1–5 each, with a reason)

  • hook, technical_accuracy, grounding
  • voice, clarity, cta

Hard-fail flags

  • unsupported_claim: any clause not in the evidence
  • off_brand: banned wording, hype, leaked ids, unlabelled demo claim

Code's decision

average  = sum(scores) / 6
accepted = average ≥ 3.5
           AND no hard-fail flag

4,5,2,4,4,3 → 3.67, but unsupported_claim
            → REJECTED
all 3s      → 3.0 → REJECTED
  • Checks every claim, including uncited ones; background knowledge doesn't count as evidence.
  • The answer form is built from the rubric at runtime (review_wire_schema), so adding a criterion needs no code.
  • Broken form → one repair → still broken → failed_output. A broken review never approves.
  • Only reasons below 3.5 and hard-fail reasons go back to the writer.
  • Retry node: attempt 1 rejected → writer again; attempt 2 rejected → dropped_quality.
  • reasoning_effort: medium, the only agent that pays for thinking.
Weak spot: writer and reviewer use the same model, and LLM judges tend to favor their own style. A different model family is a one-line change in agents/reviewer/agent.yaml.

08

Advisor

LLM Looks back at the run and suggests instruction edits. A human applies them, or doesn't.

Reads

  • Evidence: research log, drafts, review report, final
  • Editable files only: brand-voice.md, each type's writer.md and rubric.md, with fingerprints

Code rejects any edit that

  • targets another file, or a changed file (fingerprint)
  • has a before that isn't unique
  • touches YAML front matter (machine rules)
  • adds or changes a line with digits
  • makes a patch over 16,000 chars

Output: advice.md (up to 10 recommendations) and advice.patch (a unified diff), always written. Apply with git apply output/<run>/advice.patch. Failure is recorded and never touches the posts.

Why suggest-only: a system that rewrites its own prompts can drift or loosen its own rubric. Code limits what the advisor can change; the human reading the diff judges whether it should.

Budget and resume

The ledger: money is set aside before it's spent

stateDiagram-v2
  [*] --> reserved: reserve (fits budget)
  reserved --> dispatched: sent
  dispatched --> confirmed: answer, settle real numbers
  dispatched --> uncertain: no answer, may be billed
  reserved --> released: crash before sending
  dispatched --> uncertain: crash after sending

Reserve rule: add every entry that isn't released, including calls in flight. If this call's worst case crosses the token or dollar budget, refuse it: that slot becomes failed_budget, the others continue. A lock makes the six lanes take turns.

A guard, not a perfect cap: input is estimated (chars / 3.5 + 15%), so a call can overshoot slightly, recorded as overshoot_tokens.

Resume

python run_week.py --resume output/20261016T091500-a1b2c3d4 --token-budget 400000
  1. Read-only preflight: snapshot fingerprints match, ledger and records valid, checkpoint exists, budgets only rise.
  2. Lock the folder. Already finished? Return the saved summary.
  3. Reopen the ledger: reserved → released, dispatched → uncertain (kept on the bill).
  4. graph.ainvoke(None, config) continues from the checkpoint.
  5. Research, review, visual and advisor reuse saved records whose input_sha256 matches, so re-runs are free.
  6. The budget is lifetime: five resumes don't get five budgets.
Can't promise: a call billed just before a crash, whose result wasn't saved, is made again. It's documented and kept as an uncertain charge.

Interview cheat sheet

Each answer has a short version to say first, and a follow-up if they push.

Architecture

Why a workflow and not a fully autonomous agent?

The steps never change: research, write, check, review, illustrate, export. Code fixing the order makes runs predictable, cheaper and testable, and one failure can't confuse the control flow.

If they push: agency is used where it helps. Research is a bounded agent loop: the model chooses between knowledge-base search, web search and finishing, but code makes the first search, runs the tools, caps it at 4 searches and 5 turns, and verifies every cited source.

Why these agents and not more or fewer?

Each owns one kind of judgment: finding evidence, writing, judging, choosing image text, suggesting improvements. Anything code can do exactly (validation, export, summary, routing) isn't an agent.

If they push: a separate fact-checker would duplicate the reviewer's job, which the brief penalizes. Two writers exist because threads and marketing posts have different rules, but they're the same class configured by files.

Why LangGraph?

The pipeline is a small state machine. LangGraph gives typed state, parallel lanes with Send, visible conditional edges for retry-or-drop, and a checkpointer for resume.

If they push: it's used for orchestration only. Agents are plain Python classes testable without the graph; graph nodes are thin glue. That keeps "no agent doing another agent's job" visible in code.

How do agents hand off work?

Through typed Pydantic contracts: ResearchPack → Draft → ValidationResult → Review → ImageSpec. Each agent gets one input object and returns one output object, and never sees the week state.

If they push: each slot carries a SlotState card where every station fills only its own field. Identity checks (slot id and attempt) stop a result landing on the wrong card.

Grounding and quality

How do you stop hallucinated claims?

Three layers. The writer only sees its research pack and must cite source ids per tweet. Code checks every cited id exists with usable evidence. The reviewer checks every factual clause, cited or not, against the evidence text, and any unsupported claim is a hard fail.

If they push: background knowledge doesn't count as support, words like "most" or "prevents" need evidence, and the writer is told never to be more specific than the evidence. A --set topic is not evidence.

What does "rules in code, judgment in the model" mean here?

Banned characters, hashtags, links, length, tweet count and citation ids are checked by the validator, never by an LLM. The reviewer gives scores; code computes the pass decision.

If they push: the validator runs before the reviewer, so we never pay an LLM to judge a post that already broke a rule. Numbering is added by code before validation, so the checked text is the exported text.

How does the reviewer decide?

It scores six rubric criteria from 1 to 5 with reasons and sets two hard-fail flags. Code accepts only if the average is at least 3.5 and no flag is true.

If they push: the answer form is generated from the rubric file, so criteria are configurable. A malformed review gets one repair and then fails closed. A broken review never approves.

What's the retry policy?

One content retry per post, as the brief says. A rejection by the validator or the reviewer sends feedback and the rejected draft back to the writer; a second rejection drops the post with its reasons.

If they push: API failures and cut-off answers are separate: up to 3 transient retries with backoff, one retry at 1.5x output for truncation, one repair for malformed output. None of those spend the content retry.

Would you post the output as-is?

That's what the gates aim for: brand rules enforced in code, every claim grounded, a rubric pass bar, and images that only reuse grounded text.

If they push: the honest risk is the reviewer sharing the writer's model. I'd switch it to a different model family and add a small eval set with planted unsupported claims.

Reliability and cost

What happens if the API dies mid-run?

That call retries up to 3 times with backoff. If it still fails, only that post fails with failed_api; the other lanes continue, and export and summary always run.

If they push: the run can be resumed. The checkpointer saved finished steps, saved records make re-run steps free, and calls sent but never answered stay on the bill as uncertain charges.

How do you control cost?

A ledger reserves each call's worst case before sending it. If the run's token or dollar budget would be crossed, the call is refused and that post fails with failed_budget.

If they push: it's a pre-call guard, not a perfect cap, since input tokens are estimated. Real tokens come from the provider's usage data, cost from the provider or genai-prices, and the summary reports confirmed and uncertain spend separately.

How do you measure tokens across providers?

LangChain's normalized usage_metadata, read from the raw response even with structured output. Missing counts are estimated and flagged.

If they push: each attempt writes a receipt to usage.jsonl with cached and reasoning tokens, cost source, overshoot versus the reservation, finish reason and failure kind.

Why can't resume guarantee exactly-once billing?

If a call is billed but the process dies before saving its result, there's no record to reuse, so resume calls again. The design documents this rather than overclaiming.

If they push: the ledger marks a call "dispatched" before sending; after a crash those become uncertain charges kept in the budget, so spend never disappears.

Extensibility

How do you add a post type?

Add a folder under post_types/ with type.yaml, writer.md, rubric.md and research.md, and an agent folder if it needs its own writer. The orchestrator never names a post type.

If they push: type.yaml sets the writer, rubric, tweet range, numbering, topic source, pass bar, hard-fail flags and visual template. A type needing a new stage would need code.

How would you grow to 15 slots?

The graph doesn't change: more slots means more Send lanes. Raise the budget and use --max-concurrency for provider rate limits.

If they push: with a bigger knowledge base, swap BM25 for embeddings inside search_kb, a one-file change. Topic de-duplication already runs in one place.

How would you add a second platform?

Make the platform an explicit capability: character limit, thread support and export format per platform, with exporters as adapters like the image backends.

If they push: today 280 is locked in three places on purpose, so a config typo can't produce posts X won't accept. Removing that lock is a deliberate design change, not a setting.

Why can't the advisor edit files itself?

Observability and security

How do you debug a bad post?

What security risks did you consider?

Prompt injection from web pages (evidence is treated as data), SSRF (only public URLs are fetched, redirects re-checked), path traversal (safe names, image paths kept inside the run folder), and secrets (keys only from .env, error output redacts details).
